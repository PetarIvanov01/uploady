# Uploady Web — agent handoff

This is the authoritative context document for agents working on `apps/web`.
It is organized for a context-free coding session: start here, then open only
the files named for the feature being changed.

## Role in the monorepo

`@uploady/web` is the React 19/Vite client for the Uploady hierarchical file
vault. It provides:

- root, nested-folder, and file-detail routes with TanStack Router;
- end-to-end typed API calls through Elysia Eden Treaty and `@uploady/api`;
- folder creation, rename, nested creation, and cascading deletion UI;
- root-level direct-to-S3 file uploads with progress and completion checks;
- client-side search over the currently loaded folder.

The active vault UI is `FolderView`.

## Agent startup contract

Every new Codex agent must first follow the `onboard-uploady-project` skill in
`.codex/skills/onboard-uploady-project/SKILL.md`. Any frontend route, loader,
component, behavior, styling architecture, tooling, or end-to-end contract
change must update this README in the same change so it remains an accurate
context handoff.

## Stack and build behavior

- React 19 with Strict Mode.
- Vite 8.
- TypeScript 7 with strict mode and project references.
- TanStack Router with file-based routes and generated route tree.
- Eden Treaty for types derived from the backend's exported Elysia `App`.
- Tailwind CSS 4 through the Vite plugin.
- Space Mono through `@fontsource/space-mono`.
- React Compiler through Rolldown/Babel and `reactCompilerPreset()`.

`vite.config.ts` runs the TanStack Router plugin before React, enables automatic
route code splitting, and proxies `/api` to `http://localhost:3000` in local
development.

## Route map

| Browser route       | Source                            | Loader and rendered behavior                                                     |
| ------------------- | --------------------------------- | -------------------------------------------------------------------------------- |
| `/`                 | `src/routes/index.tsx`            | Loads `GET /api/v1/vault`; renders the root `FolderView`.                        |
| `/folder/$folderId` | `src/routes/folder/$folderId.tsx` | Loads `GET /api/v1/vault/folders/:id`; renders breadcrumbs and direct contents.  |
| `/file/$fileId`     | `src/routes/file/$fileId.tsx`     | Loads `GET /api/v1/vault/files/:id`; renders its folder breadcrumb and metadata. |

All routes share `RootLayout`, which provides the Uplody header and `<Outlet>`.
The header hamburger button is visual only and has no menu behavior.

Vault and file routes have pending, error, and not-found components. Loader
data is fresh for 10 seconds (`staleTime: 10_000`). Mutations call
`router.invalidate()` to force active loader data to refresh.

`src/routeTree.gen.ts` is generated by the TanStack Router Vite plugin. Never
edit it manually. Add, remove, or rename files under `src/routes/` and let the
plugin regenerate it.

## API client and type coupling

`src/lib/api.ts` creates one Eden client:

```ts
const _api = treaty<App>(
  import.meta.env.VITE_API_URL ?? window.location.origin,
);

export const api = _api.api;
```

The `App` type comes from the workspace package `@uploady/api`, whose export
points at backend `src/app.ts`. Backend route schemas therefore control frontend
request and response types.

- In normal development, no `VITE_API_URL` is needed; same-origin `/api` calls
  go through Vite's port-3000 proxy.
- For a separately hosted API, set `VITE_API_URL` to the API origin, such as
  `https://api.example.com`, without appending `/api/v1`.
- In production without `VITE_API_URL`, the client assumes API and web share an
  origin.

After backend contract changes, run the root TypeScript check and web build;
do not duplicate backend response types manually unless mapping to a deliberate
view model.

## Active vault behavior

### Reading folders and files

`src/lib/vault.ts` requests the root or folder vault endpoint and separates the
backend's discriminated `entries` array into `folders` and `files`. It also maps
the current folder location and breadcrumbs into `VaultLoaderData`.

`FolderView` then:

- renders root-to-current breadcrumbs;
- combines folders and files for a single list;
- searches entry names case-insensitively in memory;
- navigates folder rows to `/folder/:id` and file rows to `/file/:id`;
- displays direct file/folder counts supplied for folder entries;
- formats file sizes and update dates for display.

Search is local to the already-loaded direct children. There is no recursive or
server-side search, pagination, sorting control, or filtering in the active UI.

### Folder mutations

`useFolderMutations` calls the typed `/api/v1/folders` endpoints and exposes a
single state machine for create/update/delete. `isWorkingRef` prevents two
folder mutations from running concurrently through the same hook instance.

The UI supports:

- creating a folder in root or the current folder;
- creating a folder inside a child folder from its action menu;
- renaming a child folder inline;
- renaming the current folder in the breadcrumb area;
- permanently deleting a folder and its entire subtree after confirmation.

The backend supports moving folders by changing `parentFolderId`, but the
frontend does not yet expose a move interaction.

Deletion is destructive and cascading. `DeleteFolderSheet` displays known
direct-child counts when available, warns that all descendants will be removed,
and requires an explicit confirmation checkbox. After deleting the folder
currently being viewed, the UI navigates to its former parent or root; after
deleting a child, it invalidates the current route.

### File upload

`FileUpload` is enabled only at the root. In nested folders it is intentionally
rendered disabled because the backend upload contract has no `parentFolderId`.

The active upload state machine is implemented in `useFileUpload`:

1. reject empty files and files above 200 MiB;
2. read the entire file into memory and calculate `sha256:<hex>` with Web Crypto;
3. initialize through `POST /api/v1/uploads/single`;
4. upload directly to the presigned storage URL with `XMLHttpRequest` so upload
   progress events are available;
5. call the backend completion endpoint;
6. show success and invalidate the current vault route.

The `Content-Type` header returned by the backend must be sent exactly to the
presigned URL. The S3/R2 bucket requires browser CORS for the web origin, `PUT`,
and `Content-Type`.

Each non-uploading phase is shown for at least 350 ms to avoid UI flicker. The
checksum implementation duplicates up to 200 MiB into browser memory, which is
a known scalability limitation. Multipart upload is not available.

### File detail

`src/lib/files.ts` maps a backend `404` to TanStack Router `notFound` and wraps
other failures in `FileLoadError`. `FilePage` shows a root-to-file breadcrumb,
with navigable containing folders and a non-navigable file name, followed by
the file's name, size, MIME type, status, creation time, and ID. Long breadcrumb
labels truncate with an ellipsis and expose their full value as a title.

There is no preview, download button, version history, rename, move, or delete
behavior for individual files. The backend also does not expose these yet.

## Styling conventions

- Tailwind v4 is imported directly from `src/index.css`.
- Project design tokens are declared in the CSS `@theme` block: paper/panel,
  surface, ink/muted/faint, borders, accent, destructive, and mono font.
- Components use utility classes inline; there is no CSS module or component
  library abstraction.
- Interactive controls target roughly 44 px minimum touch height.
- Focus-visible and reduced-motion defaults are global.
- Reuse `Button`, `VaultIcons`, tokens, and existing spacing before introducing
  a second styling system.

## Local development and commands

Start the API and web independently from the repository root:

```bash
npm run dev:api
npm run dev:web
```

The web app defaults to Vite's `http://localhost:5173`; the proxy expects the
API at `http://localhost:3000`.

Useful commands:

```bash
npm run build --workspace @uploady/web
npm run lint --workspace @uploady/web
npm run format --workspace @uploady/web
npm run check
npm run dead-code
npm run dead-code:files
npm run build
```

Oxlint handles issues within reachable source files. Root-level Knip handles
unused files, exports, and dependencies across both workspaces;
`dead-code:files` limits that analysis to unreachable files. Keep Knip's
configuration narrow, and investigate a finding before adding an exclusion.

There is currently no web test script or automated frontend test suite. A root
`npm run test` exercises packages that define test tasks, which currently means
the API behavior rather than browser components.

## Error and state conventions

- Loader `404`s become TanStack Router not-found states.
- Other API response failures use `responseErrorMessage` to extract Elysia's
  `{ value: { message } }` shape with a stable fallback.
- Unknown mutation/upload failures use `unknownErrorMessage`.
- Abort signals from TanStack loaders are forwarded to Eden fetch calls.
- Folder mutations return `null`/`false` on handled failure and expose the
  message through hook state; callers invalidate only after success.
- Upload state is a discriminated union: `idle`, `preparing`, `initializing`,
  `uploading`, `verifying`, `success`, or `error`.

## Invariants for future agents

- Do not edit `routeTree.gen.ts`.
- Preserve the Eden `App` type connection; do not replace typed calls with raw
  `fetch` for ordinary API requests. Direct storage upload is the exception.
- Keep object uploads direct to storage; do not send large bodies through the
  Elysia API unless the architecture is deliberately changed.
- Do not enable nested uploads until the API persists `parentFolderId`.
- Treat folder deletion as recursive and permanent in copy and confirmation UI.
- Invalidate TanStack Router data after successful mutations that affect the
  visible vault.
- Keep `null` distinct from omission for `parentFolderId`: null means root;
  omission means do not change the parent in a PATCH.
